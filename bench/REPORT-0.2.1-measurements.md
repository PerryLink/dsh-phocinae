## 0. 先给结论

| 问题 | 答案 |
|---|---|
| 能省多少 token？ | **取决于升级阈值。**随大模型一起用、τ=0.4 时 **省 93.3%**；纯本地 **省 100%（0 计费 token）** |
| 省 token 伤不伤效果？ | **在τ=0.4 及以下不伤**（0.7305 vs 纯大模型 0.7085）；**τ=0.6 及以上反而更差**（0.7115） |
| 插件自己花多少 token？ | 每次请求 **685 token 固定开销** + 每个决策 **234 token**；摊薄后占比 30% → 7.7% |
| 审批门花多少 token？ | **0**。`tools/pre-execute` 是钩子不是消息 |
| 审批门准不准？ | 53 条标注命令 **危险命令拦截率 1.0000，0 条漏放** |
| 延迟？ | 单次本地决策 **42.6 ms**；门控筛命令 **21 ms**；白名单命令 **0.02 ms** |

**最重要的一条**：这个版本**没有**实现"自动省 82%"——它产生的是**升级信号**，省多少由调用方决定。τ 选在哪里，是你自己的取舍。

## 1. 实验设计

三种策略，全部在**同一批 2000 个决策**上测：

| 策略 | 含义 |
|---|---|
| **LLM-ONLY** | 每个用例都交给 `deepseek-flash`，token 由 API 的 `usage` 精确计量 |
| **LOCAL-ONLY** | 每个用例都交给本地斑海豹，**计费 token 恒为 0** |
| **HYBRID(τ)** | 本地先答；置信度低于 τ 的用例升级给大模型。**这就是 `escalate` 标志的用途** |

两个引擎看到**完全相同的题目与答案空间**（同一份 options / criteria 渲染）。这一点很重要：`phocinae-server` 对 `score` 题会忽略传入选项、固定要求 2–10 九级量表，而数据集实际是 4 级 0-based，所以我把 `score` 统一表达为"对 4 个等级描述做 choice"——两个引擎拿到同一个四选一，标签不用换算就对得上。

> ⚠️ **口径说明（关系到绝对值）**：本实验里两边都只看等级描述文本、看不到原始 `instructions`，所以两边的绝对准确率都**低于**各自单引擎的公布值（本地 0.7320 vs README 复现的 0.7825；大模型 0.7085）。这是**对等的**比较，但绝对值不可与 README 那张表直接并列。

## 2. Token 计量

### 2.1 大模型一次决策的真实成本

400 例全部走 `deepseek-flash`，token 数取自每次响应的 `usage`：

```
total 1,222,211 tokens  =  290,606 prompt + 931,605 completion
per case 3,055.5 tokens  (每个用例问 5 个决策)
```

**3,055 token/决策组（约 611 token/决策）**，其中 76% 是输出 token——因为要在 JSON 里写出答案。

### 2.2 插件自己花多少

用 API 自己的分词器量（`max_tokens=1`，只读 `prompt_tokens`）：

| 项 | token | 说明 |
|---|---|---|
| `phocinae_ask` 工具定义 | 473 | **每个请求常驻** |
| `phocinae_gate` 工具定义 | 212 | **每个请求常驻** |
| 固定开销小计 | **685** | 会话内摊薄 |
| 一次调用的入参 | 99 | 每次决策 |
| 一次调用的返回（渲染后） | 135 | 每次决策 |
| **单次冷启动决策** | **919** | 685 + 234 |
| **稳态每个决策** | **234** | 固定开销已摊完 |

### 2.3 摊薄曲线

| 决策数 | 本地路径 | 大模型路径 | 本地占比 | 省 |
|---|---|---|---|---|
| 1 | 919 | 3,056 | 30.1% | 69.9% |
| 5 | 1,855 | 15,278 | 12.1% | 87.9% |
| 10 | 3,025 | 30,555 | 9.9% | **90.1%** |
| 25 | 6,535 | 76,388 | 8.6% | 91.4% |
| 100 | 24,085 | 305,553 | 7.9% | 92.1% |
| 1000 | 234,685 | 3,055,528 | 7.7% | **92.3%** |

**纯本地路径的省率饱和在约 92%**，不是 100%——因为插件的工具定义与调用往返要走调用方自己的上下文。单次决策时只有 69.9%（冷启动开销占大头），**这就是"省 82%"这类数字的合理区间上限**。

## 3. 混合策略：省 token 与效果的真实取舍

| 策略 | 升级率 | token | 省（仅模型） | 省（含插件开销） | **准确率** |
|---|---|---|---|---|---|
| LLM-ONLY | 100% | 1,222,211 | 0% | 0% | 0.7085 |
| **LOCAL-ONLY** | 0% | 0 | 100% | **92.3%** | **0.7320** |
| HYBRID τ=0.30 | 0.3% | 3,056 | 99.8% | 92.1% | 0.7315 |
| **HYBRID τ=0.40** | 6.8% | 82,499 | 93.3% | **86.1%** | **0.7305** |
| HYBRID τ=0.50 | 57.0% | 696,660 | 43.0% | 39.7% | 0.7065 |
| HYBRID τ=0.60 | 90.8% | 1,109,156 | 9.2% | 8.5% | 0.7115 |
| HYBRID τ=0.70 | 99.3% | 1,213,044 | 0.8% | 0.6% | 0.7085 |
| HYBRID τ=0.90 | 100% | 1,222,211 | 0% | −0.1% | 0.7085 |

**读法**：

- **τ=0.30–0.40 是甜蜜点**：省 86–92%，效果与纯本地持平（0.7305–0.7315），比纯大模型还好。
- **τ=0.50 起急剧恶化**：57% 的用例被升级，只省 43%，而且准确率**掉到 0.7065，比两个极端都差**。
- **τ=0.60（模型卡宣称的冻结值）在本负载上有害**：升级 90.8% 的用例，只省 9.2%，准确率 0.7115 < 纯本地 0.7320。τ=0.90 甚至因为插件开销出现**负节省**。

τ=0.60 之所以有害，原因很直接：**在这个负载上大模型比本地小模型更差**（0.7085 vs 0.7320），把不确定的题交给更差的裁判，等于把本地答对的那些也改错。分题型看：

| 题型 | n | 本地 | 大模型 |
|---|---|---|---|
| choice（含 score 改写） | 1400 | **0.7529** | 0.6793 |
| noul | 600 | 0.6833 | **0.7767** |

大模型只在 `noul` 上有优势（+9.3pp），在 `choice` 上差 7.4pp。按**用例**升级（一个用例里 5 题一起重答）会把 choice 题一起改坏——这正是 τ 越大越差的原因。

置信度分布（n=2000）：min 0.272 / p25 0.533 / **中位 0.629** / p75 0.760 / p90 0.883 / max 0.969。中位数在 0.63，所以 **τ=0.6 天然会把一半以上判为"不确定"**——这是"压缩置信度"的直接后果，也是 τ 必须选低的原因。

## 5. 审批门指标

53 条标注命令（31 条危险 / 22 条良性），通过**插件真实门**（`lib/guard.mjs` 的 `decideToolCall`）测量：

| 配置 | 危险拦截率 | 漏放 | 良性转人工 | 白名单直放 | 平均延迟 |
|---|---|---|---|---|---|
| **0.2.1 出厂默认**（harm + minConf 0.45 + 白名单） | **1.0000** | **0** | 6/22 | 16 | **15.7 ms** |
| harm，去掉白名单 | 1.0000 | 0 | **22/22** | 0 | 20.8 ms |
| harm + 白名单 + minConf 0.6 | 1.0000 | 0 | 6/22 | 16 | 14.0 ms |
| tri-state | 1.0000 | 0 | 6/22 | 16 | 15.3 ms |
| **noul（0.1.2 原样）** | **0.0000** | **31** | 0/22 | 16 | 13.8 ms |

要点：

- **出厂默认 31 条危险命令一条没漏**，且只把 6/22 条良性命令转人工——剩下 16 条走白名单，**不计入 token 也不计入延迟**。
- 去掉白名单后，良性命令 **22/22 全部转人工**。这印证了 README 里的设计判断：模型置信度太压缩，不适合当通用过滤器；**白名单不是优化，是必需的**。
- `noul` 原样保留作为对照：**31 条危险命令全部放行**，跟上一轮审计的结论一致。
- **门控不产生任何会话 token**——它是 `tools/pre-execute` 钩子，不是消息。这是它相对"让大模型审每条命令"最大的优势：**零 token 成本**。

## 7. 怎么用这些数

**建议配置**（想要省 token 且不掉效果）：

```yaml
- id: phocinae
  config:
    escalateAt: 0.4          # 升级信号阈值：实测甜蜜点
    gate:
      mode: harm             # 出厂默认，危险拦截率 1.0
      minConfidence: 0.45    # 出厂默认
      autoAllow: [...]       # 保留白名单；去掉它会让所有良性命令转人工
```

**什么时候不要用**：

- 你的负载里大模型**明显强于**本地小模型时，低 τ 是纯赚，但**高 τ 会伤害效果**——上表 τ≥0.5 已经证明。上生产前请用 `bench/token-savings.mjs` 在你自己的流量上重跑一遍再定 τ。
- 需要"每一条命令都有人审"时——那用 `gate.autoAllow: []`，代价是良性命令全部转人工。

**不要相信的**：

- 模型卡说的"τ=0.6 省 82%"。本实测：**τ=0.6 在 typed-decisions 上只省 9.2%（含插件开销 8.5%），且准确率低于纯本地**。82% 属于 τ≈0.50 的"升级率"口径，而那个口径下效果已经掉到 0.7065。
- 把"本地决策"当成零成本。它有 **685 token/请求的固定开销**；单次决策时占 30%。
